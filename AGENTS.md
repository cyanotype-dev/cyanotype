# Cyanotype

Cyanotype generates instruction files for coding agents (CLAUDE.md, AGENTS.md, Cursor and Copilot rules) from a catalog of choices, and backs critical rules with real constraints. `docs/DESIGN.md` is the source of truth: read the relevant section before implementing anything.

**Current phase: Phase 0 (foundations).** Out of scope until later phases: TUI, desktop app, MCP server, release tooling. Do not start them, even partially.

## Language policy

- Code, comments, docs, commit messages and CLI output: English.
- Replies to the maintainer: Italian.

## Tech stack

- Go, version pinned in `go.mod`. Module path: `github.com/cyanotype-dev/cyanotype`.
- CLI: `spf13/cobra`.
- Any other dependency needs approval first. Why: Cyanotype ships as a single binary, and every dependency is supply-chain risk.

## Commands

- Build: `go build ./...`
- Test: `go test ./...`
- Lint: `golangci-lint run`
- Run: `go run ./cmd/cyanotype`
- Release check: `goreleaser check`; snapshot: `goreleaser release --snapshot --clean --skip=sign` (Linux or macOS only)

## Project structure

- `cmd/cyanotype/`: CLI entry point. Thin: parses flags, calls `internal/`, prints results.
- `internal/catalog/`: loads and validates catalog entries.
- `internal/spec/`: reads and writes `cyanotype.yaml`.
- `internal/resolve/`: compatibility, conflicts, presets.
- `internal/detect/`: stack detection in existing repos.
- `internal/render/`: one renderer per agent format.
- `internal/generate/`: compares rendered files with the project and writes them safely (atomic, root-confined, never deletes).
- `internal/diff/`: line diff with unified output.
- `internal/preset/`: loads presets from the catalog and validates them by resolving them against it.
- `internal/simple/`: simple-mode questions and how their answers become a spec.
- `internal/lock/`: reads and writes cyanotype.lock, the record of what cyanotype generated.
- `internal/check/`: drift detection for cyanotype check; findings are plain data, never printed.
- `catalog/`: YAML entries, licensed CC0-1.0 (separate LICENSE). Code is Apache-2.0.
- `schema/`: JSON Schemas for catalog entries and the spec file.
- `.goreleaser.yaml`, `packaging/`: release configuration, run by `.github/workflows/release.yml` on v* tags. See docs/RELEASING.md.

## Code style

- `internal/` packages never print, read stdin or exit. Why: the same core will serve CLI, TUI, desktop and MCP.
- Return errors, never panic in library code. Wrap with `fmt.Errorf("...: %w", err)`, lowercase messages.
- Keep packages small and focused; define interfaces where they are used.
- Write code that is easy to learn from: idiomatic Go, clear names, and doc comments on every exported identifier explaining what it does and why it exists. Why: the code doubles as learning material for Go.

## Testing

- Table-driven tests for logic; golden files in `testdata/` for generated output. Why: renderers must produce exact files.
- Never edit, skip or delete an existing test to make it pass. Fix the code, or stop and ask.
- Change catalog permission rules (enforce.claude) only together with a run of docs/enforce-checks.md, recorded there. Why: go test cannot check what Claude Code matches at run time; this run found npm.cmd and pip -q install getting around rules that looked complete.

## Git workflow

- One branch per task, merged through a pull request. Never commit directly to `main`.
- Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`), small commits.
- Order commits so each one builds and passes tests on its own, catalog data before the code and tests that depend on it. Why: small commits only help bisect and revert when every one of them is green.

## Agent workflow

- For anything beyond a one-file change, propose a plan and wait for approval.
- Done means: build, tests and lint pass, and you show their output.
- Never create alternative copies of files (`_v2`, `_new`). Edit the original.
- Do not edit this file. If you learn a convention or get corrected twice on the same point, propose a rule with its reason.
- Update docs/DESIGN.md in the same PR whenever a design decision changes. Why: agents read it before implementing, so a stale decision misleads them.
- If a tool or permission check fails or does not allow an action, stop and tell the maintainer. Never reach the same result through another tool, such as writing files with Bash when Edit is blocked. Why: guardrails only work if nobody routes around them.

## Safety rules

- No destructive commands (`rm -rf`, `git reset --hard`, `git push --force`, deleting branches) without asking first.
- Never commit secrets; they belong in environment variables, never in the repo.
- Never create, move or push tags, and never run `gh release`. Why: a pushed v* tag publishes a signed release to every channel; only the maintainer releases.
